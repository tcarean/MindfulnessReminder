# Requirements

The source of truth for behaviour. Code follows this file, not the reverse. A behaviour change is
first an edit here (status `draft`), then a test, then code (status `implemented`), and the design
note of its area changes in the same task (the kit's rules "Requirements first" and "Design
notes"). Until 2026-10-09 the behaviour was described by the code, its comments, `CLAUDE.md` and
the user documentation; that day `CLAUDE.md` was split into this file, `docs/decisions/` and
`docs/design/` (ADR 0001).

Rules for entries:

- IDs are `R-NNN`, assigned once, never reused. A dropped requirement keeps its ID with status
  `dropped`. Gaps in the numbering are deliberate: each block of ten is one area.
- Status is one of `draft`, `accepted`, `implemented`, `dropped`. `implemented` means a test
  named `R###_...` exists in `tests/MindfulnessReminder.Tests` (`RepoInvariantTests` checks it
  both ways). `accepted` means the behaviour is agreed and in the code, and no test carries the
  ID. On 2026-10-09 that is the App layer, `src/MindfulnessReminder.App/`, which has no unit
  tests by design (ADR 0008) and is checked by launching the application, with `--preview` or
  from the tray.
- Describe observable behaviour, with one concrete example that includes numbers. No adjectives.
- Error behaviour is a requirement too.
- Constants are quoted by their name in the code and their value on 2026-10-09; the code holds the
  value, this file the meaning.
- There are no validation figures (ADR 0005). Every number below is a constant in the code; the
  tests use most of them by name, not by value, so a changed value keeps them green, and the row
  that states it changes first (the kit's rule "Requirements first").

The user documentation of the same behaviour is `README.md`; the explanations behind each row are
in `docs/design/` and `docs/decisions/`.

## The tray, one instance, auto-start

| ID | Status | Requirement |
| --- | --- | --- |
| R-001 | accepted | The application has no main window and no taskbar entry: it lives in the notification area, with the icon `Assets/app.ico`, embedded in the executable and drawn at `SystemInformation.SmallIconSize`. Right-clicking it opens a menu of four items, in this order: `Settings...`, the checkbox `Run at Windows startup`, a separator, `About`, `Exit`. `Exit` ends the process. Example: hovering the icon right after a start shows `Mindfulness Reminder 1.4.0 - next in 30 min` (R-060). |
| R-002 | accepted | One copy runs per Windows session: the first claims the session's named mutex `Local\MindfulnessReminder.SingleInstance`, and a second copy started while it is held exits at once, with no message and no tray icon. `--preview` and `--detect` (R-045, R-080) do not claim the mutex and run beside the copy in the tray. Example: the Run entry starts a copy at logon; a double-click on the executable afterwards starts nothing. |
| R-003 | implemented | On the very first run, when `HKCU\Software\MindfulnessReminder` has no value `AutoStartInitialized` and the startup status is `Disabled` (R-004), the application registers itself for Windows startup: it writes the quoted path of the running executable (`RegistryAutoStartManager.Command`) as the value `MindfulnessReminder` under `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` and lifts a Task Manager veto it can read, as a click does (R-005), writes `AutoStartInitialized` as `1`, and shows the balloon `Running in the tray. It now starts with Windows -- untick that in the tray menu to stop it.`, titled `Mindfulness Reminder`. When the status is anything else, an entry is already there: the first run treats it as a later run does (R-006), repairing its path and keeping a Task Manager veto, writes the marker, and shows no balloon. Every later run leaves the registration alone, so an entry the user removed stays removed. A blank executable path is rejected. The first run reads the Run value before it writes anything, so an entry it may not read stops it. A read or write refused while registering (`SecurityException`, `UnauthorizedAccessException`, `IOException`, as in R-051) does not stop the application: no registration is made, no marker is written, and the next start tries again; a path already repaired stays repaired. When the refusal comes after the Run value was written, from the Task Manager key or the marker's key, the run deletes that value again. Example: an executable at `C:\Tools\MindfulnessReminder.exe` is registered as `"C:\Tools\MindfulnessReminder.exe"`, quotes included; a first run that finds `"D:\Old\App.exe"` switched off in Task Manager rewrites it to `"C:\Tools\MindfulnessReminder.exe"`, and it stays switched off. |
| R-004 | implemented | The startup status (`RegistryAutoStartManager.GetStatus`) is `Disabled` when the Run value is missing or blank; `BlockedByWindows` when the Run value is there and the binary value of the same name under `HKCU\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run`, where Task Manager records a veto, has a first byte whose lowest bit is set; `Enabled` otherwise. A veto without a Run value is `Disabled`. A value the account may not read (`SecurityException`, `UnauthorizedAccessException`, `IOException`) counts as missing, so reading the status never fails: an unreadable Run value is `Disabled`, and an unreadable approval value is no veto. The checkbox is ticked only for `Enabled`, and reads `Run at Windows startup (disabled in Task Manager)` for `BlockedByWindows`. Example: a first byte of `0x02` is enabled, `0x03` is blocked, and a `0x03` the account may not read is enabled. |
| R-005 | implemented | Clicking the checkbox while the status is `Enabled` deletes the Run value; in any other status it writes the Run value with the current path and deletes the Task Manager veto when it can read one; an approval value that is no veto, or that the account may not read, is left as it is. When Windows refuses the change (`UnauthorizedAccessException`, `SecurityException`), a balloon says `Windows refused the startup setting change. Group policy may be managing it.`; either way the checkbox is then redrawn from the registry. Deleting a value that is not there is not an error. Example: on an account that may not read the approval key, a click on the unticked checkbox writes the Run value, shows no balloon, and ticks the checkbox. |
| R-006 | implemented | On every run after the first, a Run value that holds another path than the running executable's, compared without regard to case, is rewritten with the current path; a missing Run value is not created, and a Task Manager veto is left as it is; a refused read or rewrite (as in R-003) does not stop the application. Example: after the executable moves from `C:\Tools` to `D:\Apps`, the first start by hand rewrites the entry to `"D:\Apps\MindfulnessReminder.exe"`, and Windows starts the moved copy from then on. |

## The unlock reminder

| ID | Status | Requirement |
| --- | --- | --- |
| R-010 | implemented | When the workstation is unlocked (`SessionSwitchReason.SessionUnlock`) and `ReminderSettings.UnlockEnabled` is true, the reminder window (R-070) appears with `UnlockMessage`, `WpfReminderPresenter.DefaultShowDelay` (600 ms) after the unlock. | R-012 | implemented | An unlock while a reminder window is open, or waiting out its 600 ms delay, brings that window to the front instead of opening a second, and its text stays as it was. |

| R-014 | implemented | When the pauses (R-030 to R-032) would hold the unlock reminder back, it is skipped, not postponed: nothing appears for that unlock, and the countdown the unlock restarted runs on. | R-015 | implemented | `ForegroundState.UserAway` (`QUNS_NOT_PRESENT`, 1), which Windows reports behind a lock screen and for a moment after an unlock, never holds a reminder back (R-031): an unlock while it is reported shows the reminder. |
| R-016 | implemented | Locking the workstation never shows a reminder; it suspends the countdown (R-024). |

## The periodic reminder

| ID | Status | Requirement |
| --- | --- | --- |
| R-020 | implemented | `PeriodicEnabled` is true by default, and `IntervalMinutes` is `ReminderSettings.DefaultIntervalMinutes` (30), accepted from `MinIntervalMinutes` (1) to `MaxIntervalMinutes` (480). The countdown starts with the application: a new `IntervalSchedule` counts nothing until it is started, and `Start` puts the whole interval on the clock. Example: started at 09:00:00 with the defaults, the first reminder is due at 09:30:00. |
| R-021 | implemented | One timer ticks every `ReminderCoordinator.DefaultTickInterval` (1 s). On each tick the deadline is compared with `IClock.UtcNow`: before it nothing happens; at it or after it the reminder window appears with `PeriodicMessage`, and a whole interval is put on the clock again from that moment. `CountdownChanged` is raised on every tick and on every restart. `Dispose` stops and disposes the timer. Example: started at 09:00:00 with 30 minutes, the reminder appears on the tick of 09:30:00, then on the tick of 10:00:00. |
| R-022 | implemented | A deadline that passed while the machine slept fires on the first tick after it wakes, because the deadline is a time on the clock, not a count of ticks. Example: due at 09:30, asleep from 09:20 to 11:00: the reminder appears at 11:00, and the next is due at 11:30. |
| R-023 | implemented | A periodic reminder that falls due while a reminder window is open brings that window to the front with its text unchanged, and the next interval is armed as usual. |
| R-024 | implemented | Locking suspends the countdown: the timer stops and `Remaining` is null. Unlocking puts a whole interval on the clock from the unlock, whatever was left before the lock and however long or often it was locked; an unlock without a lock restarts it too; nothing restarts while the periodic reminder is off. Example: 10 minutes left, a lock, three hours away, an unlock at 14:00: the next reminder is due at 14:30. |
| R-025 | implemented | A clock moved backwards does not postpone the reminder: when the deadline is further away than the span last armed, `TryConsumeDue` restarts the countdown from now with a whole interval. A postponement longer than the interval (R-033) is not read as a jump, and a jump during a postponement still restarts. `Remaining` is never negative. Example: due at 10:00, the clock set back from 09:50 to 08:00: the reminder is due at 08:30, not 10:00. |
| R-026 | implemented | Saving the settings (`ApplySettings`) restarts the countdown from zero with the new interval. Switching the periodic reminder off stops the countdown and the timer at once; switching it back on puts a whole interval on the clock and starts the timer. Example: 25 of 30 minutes gone, the interval changed to 10: the next reminder is due 10 minutes after the save. |
| R-027 | implemented | With `PeriodicEnabled` false no periodic reminder appears and no timer runs; the unlock reminder is unaffected. With both reminders off nothing ever appears and no timer runs. |
| R-028 | implemented | An interval outside 1 to 480 minutes given to the schedule is clamped to the nearer bound, not taken literally. Example: 0 counts as 1 minute, 1000 as 480. |

## Pausing for a call or full screen

| ID | Status | Requirement |
| --- | --- | --- |
| R-030 | implemented | With `PauseWhileMicrophoneInUse` true, the default, a reminder is held back with the reason `MicrophoneInUse` while any application holds the microphone or the camera open. The reading (`WindowsActivityMonitor`) walks `SOFTWARE\Microsoft\Windows\CurrentVersion\CapabilityAccessManager\ConsentStore\microphone` and `\webcam`, in `HKEY_CURRENT_USER` and in `HKEY_LOCAL_MACHINE`, two levels deep (the packaged applications and `NonPackaged`), and counts a key whose `LastUsedTimeStart` is above 0 and whose `LastUsedTimeStop` is 0. The camera counts like the microphone. Example: Teams in a call with the microphone muted keeps the stream open, so the reminder is held back. |
| R-031 | implemented | With `PauseWhileFullScreen` true, the default, a reminder is held back with the reason `FullScreen` while `SHQueryUserNotificationState` reports full screen or a presentation. `UserNotificationState.FromShellState` maps 5 to `Normal`, 2, 3 and 7 to `FullScreen`, 4 to `Presenting`, 6 to `QuietHours`, 1 to `UserAway`, and anything else, a failed call included, to `Unknown`; only `FullScreen` and `Presenting` hold a reminder back. The constants are the values of the Windows header's `QUERY_USER_NOTIFICATION_STATE`. Example: a game in exclusive full screen (`QUNS_RUNNING_D3D_FULL_SCREEN`, 3) holds a reminder back; `QUNS_QUIET_TIME` (6) does not. |
| R-032 | implemented | The two switches are independent: each turns off only its own check, and both apply to both reminders, whether the periodic one is on or off. When both conditions hold, the reason given is `MicrophoneInUse`. With both switches off nothing is ever held back and the activity monitor is never read (`ReminderSettings.PausesForAnything` false). Both ship switched on. |
| R-033 | implemented | A periodic reminder that falls due while held back is postponed by `RetrySeconds` (`ReminderSettings.DefaultRetrySeconds`, 20, accepted from `MinRetrySeconds`, 5, to `MaxRetrySeconds`, 300) and looked at again after each gap, for as long as the condition lasts, with no cap. It appears at the first look after the condition ends, and the next one falls due a whole interval after that. Postponing does nothing while the periodic reminder is off or the workstation is locked, and a restart puts the whole interval back over a postponement. Example: due at 10:00:00 during a call that ends at 10:47:05, with the defaults: it is looked at every 20 seconds, appears at 10:47:20, and the next is due at 11:17:20. |
| R-034 | implemented | The activity monitor is read when a reminder falls due, once per retry, and otherwise every `ReminderCoordinator.DefaultActivityRefresh` (10 s) on the idle ticks, never on every tick. `Suppression` holds the reason of the last reading, so the tooltip (R-060) names a call or full screen within about ten seconds of its start, and goes back to the countdown within about ten seconds of its end, without waiting for a reminder. |
| R-035 | implemented | An unlock, a lock and a save of the settings clear the held-back state (`Suppression` back to `None`); after a lock or a save, the next idle tick reads the monitor again. |

## Messages and the Settings window

| ID | Status | Requirement |
| --- | --- | --- |
| R-040 | implemented | Each reminder has its own message, `UnlockMessage` and `PeriodicMessage`, both `ReminderSettings.DefaultMessage` (`Ground yourself`) by default and each at most `MaxMessageLength` (50) characters; each message box of the Settings window accepts at most that many characters (`MaxLength` bound to the constant). |
| R-041 | implemented | `ReminderSettings.NormalizeMessage` turns carriage returns, line feeds and tabs into spaces, trims, reads an empty or missing text as `Ground yourself`, and cuts a longer text at 50 characters and trims it again; `Normalize` applies it to both messages and clamps the interval and the retry gap to their bounds. Example: two spaces, `Breathe`, a tab, `out` and a line break become `Breathe out`; a 60-character text keeps its first 50 characters, less any spaces at the end. |
| R-042 | accepted | The Settings window, titled `Mindfulness Reminder Settings`, shows from top to bottom: the checkbox `Remind me when I unlock the computer` with its `Message` box; the checkbox `Remind me while I work`, `Every` N `minutes` with the hint `Between 1 and 480 minutes. The countdown restarts when you save.`, and its `Message` box; the checkboxes `Pause while the microphone or camera is in use` and `Pause during full screen and presentations`; `Check again every` N `seconds` with the hint `Between 5 and 300 seconds. The reminder waits, then looks again.`; `Save` and `Cancel`. It opens with the settings in force. A message box is greyed while its reminder is off, the interval while the periodic reminder is off, and the retry gap while neither pause is ticked. |
| R-043 | implemented | `Save` refuses, with the message shown in the window and the offending box focused and selected: a blank or over-long message of a reminder that is on (`Enter what the reminder should say, up to 50 characters.`); an interval that is not a whole number from 1 to 480 while the periodic reminder is on (`Enter a whole number of minutes between 1 and 480.`); a retry gap that is not a whole number from 5 to 300 while a pause is on (`Enter a whole number of seconds between 5 and 300.`). A field of a switched-off feature that does not read is saved as its default. `IsIntervalInRange`, `IsRetryInRange` and `IsMessageAcceptable` are the checks, and they agree with the clamp of `Normalize`. |
| R-044 | implemented | `Save` writes the settings to the registry (R-050), applies them at once (R-026) and closes the window; the new messages are used from the next reminder. `Cancel` closes it and changes nothing. |
| R-045 | accepted | `--preview` shows the reminder window once with `Ground yourself`, and the process exits when it is closed: no tray icon, no registry access, no session hook, no timer. `--preview` followed by a text shows that text after `NormalizeMessage` (R-041). Example: `MindfulnessReminder.exe --preview "Take a slow breath"`. |

## Crashes and restarts

| ID | Status | Requirement |
| --- | --- | --- |
| R-100 | implemented | The tray copy registers for automatic restart with Windows (`RegisterApplicationRestart`) right after it claims the mutex (R-002), with the command line `ApplicationRestart.CommandLine` (`--restarted`) and the flags `ApplicationRestart.Flags` (`RESTART_NO_REBOOT`, 8): Windows starts the executable again, with that argument, after a crash or a hang, and when an installer running as the same user asks it to close (one running as SYSTEM, as Windows Update's did on 2026-10-26, cannot); not after a reboot, where the Run entry starts it (R-003); and only while Windows Error Reporting is on, which it is by default. Windows applies the registration only to a process that has run for at least 60 seconds, so a copy that fails at start is not restarted in a loop (measured on 2026-10-26: restarted 0.2 s after a fail-fast at 65 s, not restarted after one at 20 s; ADR 0036). `ApplicationRestart.ShouldRegister(args)` is true for the tray copy alone: false when the arguments hold `--preview` as an argument of its own, or `--detect` alone or with `=` and a value, in any case, the shapes App reads the two switches in. A registration Windows refuses (a failed HRESULT) changes nothing but the start line of the decision log (R-111). The tests pin the two values and `ShouldRegister`; the call itself is checked by a tray start. Example: the copy started at 07:47 on 2026-10-26, whose runtime a Visual Studio update removed at 07:56, failed at 08:21 on its first reminder window and stayed down; registered, a new copy, on the new runtime, would have been in the tray within seconds of the `OK`. |
| R-101 | implemented | `CrashReport.Format(exception, banner)` is the crash dialog's text (R-076): the exception's type name, then `: ` and its message when the message is not blank (the runtime gives an empty message once its own resources are gone); a line `File: <name>` when the exception is a `FileNotFoundException`, a `FileLoadException` or a `BadImageFormatException` whose `FileName` is not blank; for each inner exception, in turn, a line `Caused by: ` with the same shape; a blank line; the banner. Example: `System.IO.FileNotFoundException: Could not load file or assembly 'UIAutomationTypes, Version=8.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35'. The system cannot find the file specified.`, then `File: UIAutomationTypes, Version=8.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35`, a blank line, `Mindfulness Reminder 1.4.0`. |
| R-102 | implemented | A copy started with `--restarted` (`ApplicationRestart.IsRestart(args)`) behaves as a plain start, the mutex and the registration included, and, once in the tray, shows the balloon `Restarted after an error. The details are in the Windows Application log.`, titled `Mindfulness Reminder`; when the first-run balloon (R-003) is due at the same start, it is shown first and this one replaces it, the tray showing one balloon at a time. `--preview` and `--detect` ignore the argument. The tests pin `IsRestart`; the balloon is checked by a tray start. Example: after the crash in R-076, the new copy shows the balloon once and then behaves as before, with the countdown started afresh. |

| R-110 | implemented | The tray copy keeps a decision log: the text file `log.txt` in `%LOCALAPPDATA%\MindfulnessReminder\` (`FileDecisionLog`, in Core, given that folder by App; the one implementation of `IDecisionLog.Write`), one line per event, rendered by `DecisionLog.FormatLine(localTime, text)`: the local time as `yyyy-MM-dd HH:mm:ss`, two spaces, the text, every line break in the text replaced by ` \| `. When the file holds more than `DecisionLog.MaxBytes` (262 144) before a write, it is renamed `log.1.txt`, replacing the previous one, so at most two files exist and the newest line is always in `log.txt`. A rotation that fails (the rotated file held open) does not lose the line: it is appended, and the file grows past the cap until a later write rotates it. A write that fails for any reason (the folder cannot be created, the file is locked, the disk is full) is swallowed: the log never stops, slows or ends the application. When Windows cannot name the profile folder, nothing is written anywhere. Nothing is written on the one-second tick or on the 10-second idle reading (R-034). `--preview` and `--detect` write nothing. Example: `2026-10-26 08:17:09  Periodic reminder shown: Ground yourself`. |
| R-111 | implemented | The first line of a start, written after the restart registration (R-100): `DecisionLog.Started(banner, runtime, args, hresult)` renders `Started <banner> on <runtime>, arguments: <the arguments joined by one space, or (none)>; restart registration: ok` when the HRESULT is 0, or `; restart registration: refused (0x<HRESULT, eight hex digits>)`. `runtime` is `RuntimeInformation.FrameworkDescription`. `RestartRegistration.Register` returns the HRESULT for this line; a refused registration still changes nothing else (R-100). Example: `Started Mindfulness Reminder 1.4.0 on .NET 8.0.33, arguments: --restarted; restart registration: ok`. |
| R-112 | implemented | The coordinator writes one line per decision and none per tick: `Workstation locked`; `Workstation unlocked`; `Unlock reminder shown: <message>` and `Periodic reminder shown: <message>`; `Unlock reminder: window already open, brought to front` and `Periodic reminder: window already open, brought to front` (R-012, R-025); `Unlock reminder skipped: switched off` (R-013), `Unlock reminder skipped: one shown <N> s ago` (R-011), `Unlock reminder skipped: <reason>` (R-014); `Periodic reminder held back: <reason>, looking again every <N> s` on the first postponement and again only when the reason changes (R-033), then, when it appears, `Periodic reminder shown after <N> min held back: <message>`, or `Periodic reminder: window already open, brought to front after <N> min held back` when it finds its window open, minutes rounded up and never below 1; a lock, an unlock, a save or a clock moved back (R-025) ends a hold without a line of its own, the line of that event following, and the next hold is a first postponement again; `Settings applied: <summary>` (R-026, the summary of R-113). `<reason>` is `microphone or camera in use` for `MicrophoneInUse` and `full screen` for `FullScreen`. Example: with a 20-second retry, a reminder due at 10:00:00 during a call that ends at 10:47:05 writes `Periodic reminder held back: microphone or camera in use, looking again every 20 s` once, then at 10:47:20 `Periodic reminder shown after 48 min held back: Ground yourself`. |
| R-113 | implemented | `RegistrySettingsStore.Load` writes `Settings loaded: <summary>`, followed by `; defaults used for <value names, comma-separated, in the order they are read: PeriodicRemindersEnabled, PeriodicIntervalMinutes, UnlockReminderEnabled, UnlockMessage, PeriodicMessage, PauseWhileMicrophoneInUse, PauseWhileFullScreen, PauseRetrySeconds>` when a value was missing or did not read (R-051) and by `; clamped <name> <read> -> <kept>` for each number out of range; a key the account may not read writes `Settings loaded: <summary>; the registry refused to be read, every default used`. `Save` writes `Settings saved: <summary>`. The summary, `DecisionLog.Summary(settings)`, is `periodic <on\|off> every <N> min, unlock <on\|off>, pause for mic <on\|off>, pause for full screen <on\|off>, retry <N> s, messages "<unlock message>" / "<periodic message>"`. `StartupRegistrar` writes `Auto-start registered: <command>` on the first run that registers (R-003), `Auto-start entry repaired to <command>` when the path was rewritten (R-006), and `Auto-start: the registry refused (<exception type name>), no registration made` on a refusal (a path repaired before it stays repaired, R-003, and its own line precedes); `<command>` is `IAutoStartManager.Command`, the quoted path. Example: `Settings loaded: periodic on every 30 min, unlock on, pause for mic on, pause for full screen on, retry 20 s, messages "Ground yourself" / "Ground yourself"; defaults used for PeriodicIntervalMinutes`. |
| R-114 | implemented | The crash dialog's text (R-101) is written to the log as `Crashed: <text>`, its lines joined as R-110 says, before the dialog opens (R-076), with the same guard: a failing write does not stop the dialog or the fail-fast. Example: `Crashed: System.IO.FileNotFoundException: Could not load file or assembly 'UIAutomationTypes, Version=8.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35'. The system cannot find the file specified. \| File: UIAutomationTypes, Version=8.0.0.0, Culture=neutral, PublicKeyToken=31bf3856ad364e35 \|  \| Mindfulness Reminder 1.4.0` (the blank line folds to two separators with nothing between them). |
